## 一、冻结架构决策

1. Sub2API 是唯一账户、登录、支付、余额和计费真相源。
2. 使用具有合法商业授权的上游模型渠道。
3. PI 与 PiNovelStudio 运行在独立的内部 Node.js 服务 `novel-runtime` 中。
4. 浏览器不得直接访问 Novel Runtime 或模型网关。
5. 所有 PI 对话、小说规划、章节生成和优化产生的 LLM 调用，必须经过 Sub2API 计费网关。
6. 模型地址为服务端不可由用户修改的部署配置，不写入前端。
7. 用户不得看到模型名称、Provider、Route、系统提示词、内部工具名、候选稿、Trace 或生成策略。
8. 面向用户的 PI 不是完整编码代理，只允许小说相关能力，禁止 Shell、代码执行、任意文件和任意网络访问。
9. PiNovelStudio 保留 `novel_generate_chapter` 唯一章节生成入口和现有统一主链路。
10. 生产继续遵守“NovelOS Agentic → 作者风格整章优化 → 事实复检 → 状态提交 → 原子保存”，不得恢复旧生成链路或机器文学裁判。

## 二、目标架构

```text
用户浏览器
  └─ Sub2API Vue 前端 /novel
       └─ Sub2API Go 后端 /api/v1/novel/*
            ├─ 登录、权限、余额、支付、生成任务
            ├─ 小说项目数据与公共结果 DTO
            └─ 内部调用 Novel Runtime
                   ├─ PI Agent Runtime
                   ├─ PiNovelStudio Extension
                   ├─ 临时隔离 Workspace
                   └─ Sub2API 内部 LLM 计费入口
                            └─ 合法商业上游模型
```

建议仓库结构：

```text
sub2api/
├─ backend/internal/novel/               # 小说业务、任务、计费协调
├─ frontend/src/features/novel-studio/   # 小说功能页面
├─ services/novel-runtime/               # PI + PiNovelStudio 内部服务
├─ deploy/                               # 容器、网络、密钥和健康检查
└─ docs/novel/                           # API、计费、安全和运维文档
```

三个运行进程保持隔离，但在同一仓库、同一域名和同一部署单元中交付。

## 三、开发阶段

### Phase 0：基线与治理

#### T0-1 建立干净开发基线

- 当前 PiNovelStudio 工作树存在用户进行中的修改，禁止在现有目录直接开发。
- 从用户确认的基线提交创建独立 worktree 或集成分支。
- Sub2API 固定到明确 Commit SHA，不直接跟随 `latest`。
- 所有分支使用 `codex/` 或团队规定的集成分支前缀。

**验收：**

- 两个项目的基线 SHA 被记录。
- 当前脏工作树未被恢复、删除、暂存或覆盖。
- 可从干净检出完成原项目构建和测试。

#### T0-2 冻结业务规则

形成以下文档：

- 用户权限和页面清单
- 余额、预占、扣费、取消、退款规则
- 模型调用归属规则
- 内容安全规则
- 数据保留与用户删除规则
- 上游模型商业授权记录
- Sub2API LGPL Notice 与第三方许可证清单

### Phase 1：Novel Runtime 服务化

#### T1-1 创建 Novel Runtime

建立内部 Node.js 服务，加载：

- `@earendil-works/pi-agent-core`
- PiNovelStudio 生产构建
- 现有六个 `novel_*` 工具
- 统一章节生成入口

Novel Runtime 不提供公网端口，只接受 Sub2API 后端发出的签名请求。

#### T1-2 限制 PI 能力

生产运行时只允许小说工具白名单：

- `novel_generate_chapter`
- `novel_preflight_workspace`
- `novel_workspace_manager`
- `novel_plan_story_outline`
- `novel_strategy_policy_view`
- `novel_strategy_feedback`

明确禁止：

- Shell 和系统命令
- 任意代码执行
- 任意路径文件访问
- Git 操作
- 插件安装
- 用户指定 MCP
- 用户指定模型或接口地址
- 任意 URL 抓取
- 动态加载扩展

#### T1-3 统一模型出口

改造所有模型调用，使其只能访问：

```text
SUB2API_INTERNAL_LLM_BASE_URL
```

该配置：

- 仅存在于服务端环境或 Secret Manager
- 不出现在前端构建产物
- 不允许工作区配置覆盖
- 不允许用户输入覆盖
- 不允许失败后直连模型厂商

增加网络出口白名单，从基础设施层阻止 Novel Runtime 访问其他模型域名。

**验收：**

- 静态扫描和运行时测试均证明不存在直接模型出口。
- PI 自身对话和 PiNovelStudio 全部模型调用都经过 Sub2API。
- 未配置内部网关时必须 fail closed。

### Phase 2：身份与内部调用授权

#### T2-1 小说用户权限

增加小说功能权限：

```text
novel.access
novel.project.create
novel.outline.edit
novel.generate
novel.feedback
```

小说用户默认不能访问：

- 模型列表
- Provider 信息
- 上游账户信息
- 通用 API Key 页面
- 原始用量日志
- 管理员 Prompt Audit
- 内部生成 Trace

#### T2-2 短期任务令牌

Sub2API 为每个生成任务签发短期内部令牌，至少包含：

```text
userId
projectId
jobId
capabilities
maxCharge
issuedAt
expiresAt
nonce
```

要求：

- 使用非对称签名或独立 HMAC 密钥。
- Novel Runtime 不相信浏览器传入的用户身份。
- 用户 ID、项目归属和余额只能由 Sub2API 后端确定。
- 令牌不能被用于通用模型调用。
- 过期、重放和篡改请求必须拒绝。

### Phase 3：余额预占与逐次计费

#### T3-1 生成任务账本

新增或扩展数据表：

```text
novel_generation_jobs
novel_generation_calls
novel_balance_holds
novel_billing_adjustments
```

每个模型调用记录：

```text
jobId
callId
userId
internalStage
requestId
inputTokens
outputTokens
actualCharge
status
startedAt
completedAt
```

真实模型、Provider 和 Route 只能出现在管理员数据中。

#### T3-2 余额预占

生成任务启动前：

1. 计算预计费用区间和最大消费上限。
2. 原子检查可用余额。
3. 创建余额预占。
4. 余额不足则不进入 Novel Runtime。
5. 每次模型调用从预占额度结算。
6. 任务完成、取消或失败后释放未使用额度。

必须使用数据库事务或等价原子机制，防止并发任务透支。

#### T3-3 扣费规则

- 手工保存大纲和编辑正文不收费。
- AI 对话、AI 规划、章节生成和风格优化收费。
- 内容门禁和本地 Preflight 不收费。
- 成功产生上游用量的请求收费。
- 平台技术故障引起的重试由平台承担。
- 用户输入或内容质量引起的受控重试计入最高消费上限。
- 用户取消后停止后续调用，已经产生的用量正常结算。
- 不允许余额变为负数。
- `jobId + callId` 必须幂等。

#### T3-4 余额不足处理

余额不足分为：

- `INSUFFICIENT_BALANCE_BEFORE_START`
- `RESERVED_BUDGET_EXHAUSTED`
- `BALANCE_CHANGED_DURING_JOB`

所有情况必须：

- 停止下一次模型调用。
- 不保存未完成章节为正式章节。
- 不提交长期叙事状态。
- 保留可审计的内部失败记录。
- 向用户返回充值入口和已产生费用。

### Phase 4：小说数据与工作区隔离

#### T4-1 小说数据模型

新增：

```text
novel_projects
novel_documents
novel_document_versions
novel_chapters
novel_feedback
```

`novel_documents` 至少支持：

- CreativeConstitution
- 世界观
- 角色档案
- 故事大纲
- 作者风格档案
- ChapterSeed
- 章节正文
- 长期叙事状态

#### T4-2 临时 Workspace 适配

数据库和对象存储作为真相源。

生成时：

1. 创建任务专属临时目录。
2. 将项目快照物化为 PiNovelStudio Workspace。
3. 运行统一主链路。
4. 成功后上传章节和状态产物。
5. 原子更新数据库版本指针。
6. 删除临时目录。

失败、取消或余额不足时不得提交正式正文和长期状态。

#### T4-3 租户隔离

- 所有项目查询必须强制附加当前 `userId`。
- 禁止使用用户提交的路径。
- 禁止跨用户复用 Workspace。
- 管理员查看用户正文必须记录审计日志。
- 删除项目时同步处理对象存储、索引和缓存。

### Phase 6：内容安全与反向提取防护

#### T6-1 请求前门禁

复用 Sub2API Content Moderation 和 Prompt Guard，门禁必须位于：

```text
鉴权、格式校验之后
余额预占、模型账号选择和上游请求之前
```

阻断：

- 恶意提示词注入
- 获取系统提示词和内部配置
- 获取模型、Provider 或工具清单
- 请求执行代码、Shell 或网络操作
- 恶意软件和攻击载荷
- 明确违法危险内容
- 批量自动化滥用

#### T6-2 小说场景专用安全策略

内容审核不得把正常的虚构冲突、悬疑、犯罪描写全部误判为攻击行为。应区分：

- 虚构文学内容
- 现实可执行的危险指导
- 针对系统的提示词注入
- 恶意软件或攻击代码
- 受法律限制的内容

#### T6-3 输出防泄露

用户响应发送前检查：

- 系统提示词片段
- 内部 canary 标记
- 模型和路由名称
- 内部 URL
- 文件路径
- 堆栈信息
- 工具 Schema
- Trace 和候选策略
- API Key 或 Authorization

命中后阻断输出并生成安全事件。

#### T6-4 前端与构建保护

- 生产构建关闭 source map。
- 不打包测试、评测、Prompt 和内部配置。
- 不在浏览器 LocalStorage 保存内部令牌。
- Markdown 输出必须防 XSS。
- V1 不提供文件上传和 URL 导入。
- 所有 Cookie 使用 Secure、HttpOnly、SameSite。
- 设置 CSP、CSRF 防护和安全响应头。

## 五、明确非目标

本期不包含：

- 用户自由选择模型
- 用户自定义 API 地址
- 完整 PI 编码代理
- 用户安装插件或 MCP
- 文件上传和 URL 导入
- 多人协同编辑
- 小说公开发布平台
- 移动原生应用
- 自动机器文学裁决
- 恢复 legacy Stage0-8 链路
- 向用户开放内部 Prompt、Trace 或评测系统

## 六、最终完成定义

只有同时满足以下条件才可声明完成：

1. 登录、充值、余额和小说生成形成完整闭环。
2. 所有 LLM 调用均经过 Sub2API 并正确归属用户。
3. 并发、重试、取消和断线不会重复扣费。
4. 余额不足不会产生新的模型调用或正式章节。
5. 用户无法访问模型配置、系统提示词和内部设计资料。
6. 用户无法通过 PI 执行通用代理、Shell 或代码。
7. 多租户数据隔离通过安全测试。
8. PiNovelStudio 统一主链路和状态事务保持不变。
9. 账单、支付和生成任务可以完整审计与对账。
10. 构建、测试、安全扫描、部署演练和回滚演练全部通过。
