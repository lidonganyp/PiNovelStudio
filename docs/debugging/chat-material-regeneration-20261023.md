# 聊天修改资料后重复生成失败：第一性原理排查

日期：2026-10-23。调查对象：当前代码、项目252已保存的任务及聊天记录；修复验证使用隔离项目和stub运行时。

## 结论

资料修改、章节种子、已保存正文、叙事状态和确认方案有不同的权威与生命周期。修改大纲或角色后，并不意味着已有种子、正文、状态和确认授权都已经更新。旧约束与新资料一起进入生成，会造成持续冲突；在同一输入上重复点击，不能保证消除冲突。

本次复现并修复三处确定性实现缺陷：聊天更新角色漏递增版本；章节种子的空值无法删除旧约束；确认流程把“资料齐全”当作“旧方案仍有效”。这些是当前代码缺陷，不能反推它们就是全部历史失败的直接原因。

## 必须成立的不变量

1. 作者资料内容变化时，其版本必须变化；依赖该版本的确认授权应失效。
2. 作者删除约束后，下次生成不能继续携带被删除的旧值。
3. 资料齐全只证明字段存在，不能证明同一代资料之间不存在冲突，也不能证明旧确认授权仍有效。
4. 同一方案自己保存资料引起的版本变化，与作者后来修改资料，是两类不同的变化。只有前者允许继续原提交。
5. append必须保留既有正文；replace允许重写目标章节。修改大纲不构成覆盖既有正文的授权。
6. 新大纲描述未来计划；前章已发生事实仍受连续性检查保护。修改前章正文需要相应的状态处理。

## 已复现与修复

### 聊天更新角色不递增版本

`assistant-artifacts.ts:upsertCharacters`更新identity/personality/roleType时漏写version增量，而`computeSourceVersion`只按角色id/version识别变化。角色面板更新有乐观锁与版本增量，聊天路径没有遵守同一契约。

修复：聊天更新已有角色也递增version。测试先确认旧代码缺少该字段，再验证修复。

### 空值不能删除旧种子约束

`ensureChapterWithSeed`对mustInclude/forbiddenFacts/characterMotives/promises使用`newValue || oldValue`。新种子把某项置空时，旧约束被原样带回。

修复：完整种子载荷的这四个字段按新值写入，允许显式空字符串。intent与endingGoal仍保留必需输入保护；不修改既有正文。

### 旧方案因资料“齐全”而绕过版本校验

`confirmGenerationSteward`原先在sourceVersion不匹配时，只要readiness为ready/auto_fill就继续提交。这同时容忍了合法的“本方案刚保存资料、提交暂时失败”和不合法的“用户又改了角色或大纲”。

修复：

- 方案写完资料、提交任务前，持久化confirmedSourceVersion。
- 原版本一致时正常确认；原提交失败后，仅精确匹配这个保存检查点才允许续提。
- 后续作者修改使版本变化时返回proposal_version处理指引，不覆盖新资料、不创建任务或预占。
- 修改方案内容会清除提交恢复检查点；若资料仍未变化，将新方案绑定当前版本重新确认，防止新编辑被旧检查点跳过。
- 用户可以重新发起目标章节生成，使用当前资料继续；已提交方案仍沿用原任务。

## 验证

- 修改前，角色版本和清空种子约束两项测试失败；旧方案在资料变更后仍被放行的两项测试也失败。
- 修改后5个测试文件共84项通过：assistant-artifacts(8)、generation-steward(18)、project-context-reader(16)、jobs.service(35)、assistant-steward HTTP/数据库集成(7)。
- 两个新增HTTP用例分别验证：资料已保存但提交失败→修改角色/大纲→原方案被阻止→重新发起请求可在stub运行时成功。
- 原有“提交失败后资料不变，原方案可恢复且只创建一个任务”用例继续通过。
- API TypeScript检查通过。测试账号、项目、费率和余额均为隔离数据，结束后清理；未改项目252资料，未调用付费模型。

## 仍需区分的边界

- 大纲更新目前不会自动重写已存在的章节种子。旧种子若表达旧剧情，仍须同步修改；本次修复了无法清空旧约束的缺陷，没有自动覆盖作者种子。
- 需要修改目标章节原有段落时，应明确要求replace；append的“不覆盖原文”契约本来就限制了可修复范围。
- 前章已发生事实与新计划冲突、旧正文自身有硬伤、模型未遵循事实或正文保护要求，仍可能触发合理阻断，不能靠关闭检查来消除。
- 这次隔离测试验证资料版本与恢复流程正确，不等于证明实际模型的失败概率已经下降到某个数值。
- 修复需由后端进程加载新编译产物后生效。
