# 少量作者内测：整体优化审查与执行基线

日期：2026-10-26；验收更新：2026-10-27。第 7 节为当前实施与验收结果，前文保留排查过程证据。

## 1. 已确认的产品行为

用户已确认：

- 面向少量作者内测，首先保障写作与修改流程。
- 修改角色或大纲后，从受影响章节开始依次重写。
- 系统提出起止章节与影响理由，作者确认一次；遇到手工修改过的章节暂停提示。
- 每章成功后立即替换当前正文；失败保留已经完成的进度。
- 明确总预算内优先自动恢复；具体数值和失败收费策略授权由本轮制定。

以下默认策略已进入本地顺序重写流程；单独点击“重试原任务”是一次新的用户提交，不宣称共享此前所有独立任务的终身预算：

| 边界 | 默认值 | 执行口径 |
| --- | --- | --- |
| 每章主动执行时间 | 45 分钟 | 包括调用、退避和自动恢复；暂停时间不计，续跑不得重置已消耗预算 |
| 每章费用 | 人民币 2 元 | 恢复调用计入同一额度；供应商成本与作者收费分别记账，分别限制 |
| 每轮修订费用 | 人民币 20 元 | 成功、失败、恢复的供应商消耗都计入；到限暂停，保留进度 |
| 调用次数第二道边界 | 每章 25 次，其中恢复最多 6 次 | 复用现有预算约束；须覆盖底层真实 HTTP 重试，不能只数外层函数调用 |
| 作者收费 | 已交付章节按实际结算，最多每章 2 元 | 最终未交付章节不收费；部分完成的一轮只收已交付章节 |
| 未知用量 | 暂存预留并对账 | 不把未知用量记为零，不释放后立即重复调用 |

依据：上一轮三个成功样本平台结算分别为 0.18、0.17、0.19 元，另有约 473 秒的后台执行样本；2 元与 45 分钟给恢复留出余量。样本规模不足以证明成本分布或成功率，这些是可观测后调整的内测默认值，不是定价承诺或性能保证。供应商实际费率须从当前渠道核实，不能拿平台结算代替供应商账单。金额统一使用整数分，并显式记录人民币与供应商币种转换。

## 2. 从任务本质推导优化方向

作者购买的是“当前创作意图下，可接着写、可修改的作品正文”。因此工作单位需要同时包含：作者确认的资料、修改影响范围、每章正文、对应叙事状态、执行进度和费用。

验收成功必须同时满足：

1. 使用本轮确认的资料生成，不能用旧资料的结果覆盖新资料下的作品。
2. 第 k 章只消费与当前修订一致的前文事实；旧第 k 章及以后章节不能作为已发生事实污染重写。
3. 正文与对应状态提交成功后，才推进第 k+1 章。
4. 暂停、断线、进程重启不重复生成或收费；失败后从有效断点继续。
5. 用户能看到卡在哪章、哪个阶段、原因和已消耗预算。

文学效果仍由作者决定。沿用唯一 `novel_generate_chapter` 和正式 Agentic → 作者风格整章优化 → 故事保持/事实/完整性 → 状态与正文保存链路。

## 3. 本轮已落实：生成资料在写回前复验

### 已复现的缺陷

`platform/apps/api/src/modules/jobs/jobs.service.ts` 原本在生成前编译资料，完成时只对当前章节与种子做版本条件写入。叙事状态使用的是提交时读到的版本，不能证明它就是生成开始时的状态。角色、风格、大纲、前章发生变化时，旧模型结果仍可能进入写回。

新加的 8 个回归场景在修复前全部失败：修改角色、新增角色、增加大纲、修改风格、修改叙事状态、修改前章、修改项目类型、删除风格资料，均仍然调用正文写入。

### 改动

- 对实际编译并送给 writer 的资料计算 SHA-256 指纹；上下文观察统计不参与指纹。
- 将指纹保留在该次 HTTP 生成任务中；提交前在数据库事务内重新读取并编译资料，比较指纹。
- 缺失必要资料或指纹变化时，在正文写入前返回 `generation_materials_changed` / `material_snapshot`。
- `recoverable=false`：前端不会提供对旧资料无效的盲目重试；需要重新确认最新资料后提交。
- 最终保存使用 Serializable 事务，保留已有章节/种子的版本保护、正文版本记录、状态提交和最终账单收尾。

代码入口：

- `platform/apps/api/src/modules/jobs/jobs.service.ts`：`GenerationMaterialSnapshot`、`runHttpGeneration`、`persistGeneratedChapter`。
- `platform/apps/api/src/modules/context/failure-envelope.ts`：稳定失败码。
- `platform/apps/api/src/modules/jobs/jobs.service.spec.ts`：8 个模型运行中资料变化用例。
- `platform/apps/api/test/generation-material-snapshot.integration.spec.ts`：真实 PostgreSQL 验证角色变更、资料删除与正常交付；只使用传输占位文本，不生成小说正文。

### 验证

```powershell
node node_modules/typescript/bin/tsc --noEmit -p tsconfig.json

```

工作目录为 `platform/apps/api`。集成用例创建并清理独立测试用户与作品，未修改作者原作品；本轮未调用付费模型。

边界：指纹检查实际送给 writer 的已编译内容，不宣称覆盖尚未接入该 writer 的全部编辑器资料；指纹尚未持久化为跨进程的修订输入快照。该修复阻止旧结果覆盖，尚不自动生成替代任务。收费仍沿用现有实现，不能因为这次失败释放了 hold 就宣称已退回先前逐调用扣款。已完成 API 编译，本轮没有重启常驻服务或生产发布。

## 4. 审查发现与实施顺序

### P0-A：把现有批量能力收敛为作品修订任务

证据：

- `platform/apps/api/src/modules/chapters/chapters.controller.ts` 的 generate 接口仍提交单章任务；`jobs.controller.ts` 目前只有任务/调用明细读取。
- `jobs.service.ts` 对已有正文默认 append，不能把它直接当成 replace 重写。
- 扩展已有 `batch-generation-orchestrator.ts` / `batch-generation-job-store.ts` / `batch-generation-handler.ts`，支持逐章执行、暂停、锁、检查点和恢复。
- 批量循环调用 `isChapterAlreadyCompleted(workspaceId, chapterNumber, ...)`；判定依赖章节文件及状态 finalText 锚点，未绑定本次修订身份。因此直接用于已有章节重写会跳过旧的已完成章节。
- 批量实现中的授权/checkpoint 语义仍按逐章确认设计，需要落实本次用户明确选择的“一次确认范围”规则。

实施：

1. 资料修改保存时记录变更集合，生成有证据的影响范围建议；不确定时明确扩大候选范围并交作者确认，不能声称静态搜索能精确理解所有叙事影响。
2. 修订记录绑定用户、作品、资料指纹、起止章、预算、手工稿保护和明确 replace 模式；一次确认只授予该范围和预算内的保存权。
3. 修订幂等键绑定 revisionId + chapterId + inputFingerprint；只跳过本次修订中已成功提交的章节。
4. 恢复/重建起始章之前的权威状态，使起始章以后旧派生事实失效；保留旧正文供阅读，但标记待重写，不能作为“已发生事实”喂给模型。
5. 作者高层未来剧情意图与已发生事实分开传入；不得把剧情规划一起删除。
6. 每章正文、对应状态、修订进度一同提交后立即生效。遇手工稿、资料再次变化、预算耗尽或事实阻断时停止后续章节。

验收：同一隔离作品至少 3 章，修改角色→确认范围→依次重写；中间章失败后续跑，前章不重复、后章不越过失败章、旧未来事实不泄漏；手工稿不被自动覆盖。

### P0-B：持久化执行与阶段恢复

证据：`jobs.service.ts` 使用 `void this.runHttpGeneration(...)` 在 API 进程中派发。`onModuleInit` 清理超过运行窗口的任务并释放预占；所审查路径没有将尚在运行的任务重新接管并取回结果。

实施：复用 PostgreSQL 的持久化任务、lease、heartbeat 和结果记录；单个 worker 即可支持少量作者内测。API 请求负责提交与查询，执行结果不依赖原 API 连接存活。派发后响应丢失先查执行结果，不直接重复模型调用。

对已通过事实检查的初稿保留 checkpoint，风格失败优先恢复该阶段；绑定资料/初稿 hash、模型身份、阶段输入和预算消费。资料变化即失效，禁止重用不匹配初稿；风格仍是必经阶段。

验收：在初稿完成后、风格调用中、正文提交后分别中断 API/worker，恢复后不重复正文提交、扣款或已经完成的模型阶段。

### P0-C：费用在调用前准入，失败收费符合内测策略

证据：

- 扩展已有持久化 `budget-admission.ts` 与 `budget-ledger.ts`，不是完全没有预算控制。
- 当前 production admission 预留调用次数；`budget-ledger.ts` 的 `reservedCost: 0`，余额判断不能预留下一调用的最大实际费用。
- `platform/services/novel-runtime/src/metering-binder.ts` 等待 `tool.invoke` 完成后才逐条结算，平台 hold 不等同供应商调用前的硬费用约束。
- `billing.service.ts` 的失败 finalize 释放未使用预占，未自动退回之前逐调用结算的费用。

实施：以本章/修订同一预算账本覆盖 transport 重试、模型恢复、取消和重启；每次调用按输入 tokens、最大输出和当前费率预留费用，调用后精确结算；剩余额度不足时不派发。供应商消费与作者应付款分开记，失败消费由平台承担。采用幂等冲正或交付时收费事务，保留完整会计审计，不能删旧扣款记录伪装退款。

取消后停止派发并传递 AbortSignal；已被供应商接受的请求未必可免单，保留未决预留直至对账。单章与总预算均不得因换 jobId 或重启归零。

验收：临界额度、未知 usage、失败冲正、重复回调、取消、重启恢复及同账户并发均不重复收费；供应商消费和作者账单可解释且分别不超授权边界。

### P1-A：模型输出契约和事实检查精度

先前真实复测观察到英文写作分析混入正文 content，污染了事实锚点；样本未交付。证据见 `reports/author-style-live-20261024/solov-report.md` 及其归档。

实施：明确正文输出边界并在事实提取前检查元分析污染/空文/截断；仅在明确协议支持时分离思考字段。无法可靠区分时执行有界同阶段恢复，不粗暴删除英文，不跳过风格优化。保留否定、条件、计划与实际发生事件的语义差异，针对真实误判补双向回归。

验收：分析污染样本被拒绝或恢复；合法外文、人物计划与否定句不被误删；真实已发生关键事件被改写仍阻断。

### P1-B：平台链路进入持续验证

证据：当前 `.github/workflows/ci.yml` 运行根 npm workspace 的构建与测试；根 package.json workspace 只列扩展。平台另用 pnpm，所审查 CI 未包含平台 API/web/runtime 的独立检查。

实施：增加平台锁文件安装、Prisma 生成、API/web/runtime 编译与测试、独立 PostgreSQL 事务回归、浏览器重写/失败恢复测试。依赖越权、模型白名单、密钥隔离、账单一致性回归持续保留。真实付费模型复测独立于普通 CI，显式使用隔离作品和预算。

本地 build 产物、常驻服务、部署镜像应能返回可核对的构建身份；更新冲突的项目记忆、路由说明和过时预算注释，保持单一当前生产基线。

### P2：把作者反馈接到可验证的学习闭环

证据：平台反馈已存库，并被 `project-context-reader.ts` 读取进上下文快照；不能说反馈完全无人消费。扩展也有 `novel_strategy_feedback` 和学习模块，但所查平台提交路径没有证明它们已连成策略晋级链路。

实施：追踪“反馈→对应生成 trace/模型→作者修改差异→策略证据”的完整流向；按模型版本隔离。指标使用交付成功率、续跑成功率、作者采纳与必要修改量、每个被采纳章节的总费用和等待时间。

验收：一条作者反馈能够追到受影响策略与下一次调用证据；不能以反馈入库、自动分数或单次成功宣称文学质量提高。

## 5. 继续实施：重写输入的历史边界（2026-10-26）

### 新复现与修复

正式重写第 N 章时，API 原先读取整个章节目录，将目标章及后续旧章的标题、种子和正文末尾拼入 `story_outline`；共享 ContextCompiler 的历史关键词检索也未过滤目标章及后续章节。仅 recent chapter 层做了前章范围限制，不能阻止其他两条通道泄漏旧未来。新增的两条端到端服务/编译器回归在修复前均失败。

新实现：

- `jobs.service.ts` 的数据库查询与物化目录均限制 `chapterNumber < N`；共享 `context-compiler.ts` 同时限制历史目录与历史关键词检索。作者的 `story_outline` 和本章种子继续作为未来计划保留。
- `generation-history.ts` 从 `novelDocumentVersion` 分页查找第 N−1 章完成后的完整叙事状态，不从当前状态简单删除未来行。后者无法还原已被改写的角色值，以及第一章埋下、第五章兑现的承诺。
- 检查快照 watermark、嵌套来源和已记录的正文哈希；缺少匹配快照时返回不可盲目重试的 `generation_history_unavailable`。正常 HTTP 提交在创建任务及预占费用前就执行该检查。
- 第一章重写清空已有提交派生的状态；无章节来源、无提交 watermark 的作者初始状态继续保留。损坏 JSON 明确阻断，不静默制造空状态。
- 较早章节重写成功使当前状态 watermark 后移后，禁止越过尚未依次重建的章节、重新启用旧未来快照。
- 提交指纹额外绑定当前叙事状态的来源 hash/版本；即使 writer 使用的是历史快照，运行期间修改当前状态仍会阻止旧结果写回。

### 验证与边界

- 历史状态恢复新增 14 项单元回归，包括分页、旧正文哈希、嵌套未来来源、先前章节哈希变化、恢复期间数据库错误和禁止跳章。
- PostgreSQL 集成目标现有 8 项：包含正常恢复、缺失快照、快照哈希失配、运行中状态修改、第一章重写，以及上一轮三项资料快照用例。
- 生成/上下文/小说 API 目标在初次验证中 17 个文件、192 项通过；追加两项回归后，历史恢复与数据库目标 22 项通过。API TypeScript 检查和 Nest build 通过。
- 最终完整 API 验证：`node node_modules/vitest/vitest.mjs run --silent`，65 个文件、457 项全部通过，含真实 PostgreSQL、聊天管家、计费和权限测试，执行 64.68 秒。工作目录为 `platform/apps/api`。

这是输入边界修复，**没有完成作品级 revision 产品接入、持久化 worker 或风格阶段 checkpoint**。历史数据中的无来源事实无法仅靠文本推断确定发生章节；找不到可信历史快照时，应选择更早起点重建，不伪造旧状态。当前状态只有前章哈希检查，尚未证明完整覆盖所有未标来源的早期手改影响。

本次测试使用隔离数据和传输占位文本，没有付费模型调用，没有修改作者原作品，没有重启常驻服务或部署。

## 7. 当前实施与验收（2026-10-27）

### 根因与修复

1. 重写读取旧未来事实：重写第 N 章只消费 N 之前正文与可信 N−1 状态。冻结资料、Serializable 写回复验；JSONB 键排序导致的资料指纹误判已改为递归规范化计算。
2. 失败重复从初稿起跑：验证通过的 Agentic 初稿在风格 HTTP 前持久化，按租户、作品、章节、完整作者资料及模型身份恢复。临时绝对路径规范化为相对路径；真正资料变化不复用。恢复仍必须通过风格、故事保持、事实与完整性门。
3. 任务寿命依赖 HTTP：数据库保存执行授权和租约，runtime 保存成功/失败回执；断线重查，不重复执行已接受任务。原任务 retry 接口绑定原章节和生成模式，前端丢弃过期轮询结果。
4. 预算只数外层调用：逐真实 writer HTTP 按最大费用准入、按明确 usage 结算；语义修复也计入恢复上限。revision 更换 job 不重置成本、时间、次数。未知 usage 按最大费用占用授权预算，不当零。
5. 预算拒绝反复重试、脱敏抹掉原因：拒绝为永久 transport 错误，runtime 返回明确 envelope，revision 暂停；超时在脱敏前归类，未知用量有独立恢复原因。
6. 未交付仍记作者消费：失败章节幂等冲正，原始用量/费用不删除；作者账单及管理员收入排除退款，模型用量看板保留原始消费；transport 状态与结算同一事务提交。
7. 顺序重写：确认一次后按章执行，成功立即生效，可恢复故障在预算内自动继续；手工稿绑定精确版本确认，资料变化重新确认。明确停止后续任务，不将正在完成的章节伪装为已撤销。
8. 分析混入正文：事实提取前拒绝显式 think/analysis 块或写作自指令；风格阶段有界恢复，不删除片段冒充正文。合法外文和人物计划保留，不声称识别所有未标记思考。
