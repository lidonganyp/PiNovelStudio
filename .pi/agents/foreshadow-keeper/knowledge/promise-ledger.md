# 承诺账本手册（Promise Ledger）

> 本文件是 `foreshadow-keeper` 的唯一知识库，合并原「承诺账本 + 埋设—回收模式库」两份资料，已去重。

## 1. 台账字段

```markdown
| ID | 埋设定位 | 承诺内容(≤30字原文) | 类型 | 预期窗口 | 状态 | 距今章数 |
|---|---|---|---|---|---|---|
| PROMISE-01 | ch2#"等我回来" | 主角承诺会回来救她 | 硬承诺 | 10章内 | planted | 6 |
```

## 2. 状态机

```
planted → reinforced → partially_paid → paid
                    ↘ abandoned（仅作者可确认）
```

| 状态 | 含义 | 必要条件 |
|---|---|---|
| planted | 已埋下 | 有埋设定位 |
| reinforced | 已强化 | 至少一次再次提及 |
| partially_paid | 部分兑现 | 回应了承诺的一部分 |
| paid | 已兑现 | 回应了原始承诺且无 canon 冲突 |
| abandoned | 作者确认废弃 | 需记录废弃原因 |

## 3. 埋设—回收五种模式

| 模式 | 做法 | 风险 | 台账字段重点 |
|---|---|---|---|
| 契诃夫之枪 | 提前展示一件物品/能力，后文必须用到 | 展示了却不用 = 读者失望 | 埋设定位必须精确到"物品首次出现段" |
| 双关承诺 | 角色说的话字面成立、实质另有含义 | 回收时要让读者回看原文 | 承诺内容必须保留原始措辞（不可改写） |
| 假线索（红鲱鱼） | 引导读者怀疑错误对象 | 假线索必须有真实解释，不能是骗 | 类型标"软暗示"，并登记"真实解释 ID" |
| 延迟回收 | 强行延后并中途强化记忆 | 超过窗口易被遗忘 | 必须记录每一次强化（reinforced 次数） |
| 反向回收 | 兑现方式与原承诺相反（悲剧化） | 必须让读者觉得"合理但残酷" | 需作者确认（涉及价值观取舍） |

## 4. 承诺句式词表（抽取候选伏笔用）

- 明确的将来时："我会…""等我…""迟早…""总有一天…"
- 未解之谜："的秘密是…""他其实…""没人知道…"
- 威胁 / 预警："你最好祈祷不要…""下次见面就…"
- 道具留存："收好这个，关键时刻能…"

## 5. 强化记忆的三种手段（延后回收必备）

1. **再提及**：让另一角色提起这件事（不展开）。
2. **后果显现**：让未兑现的承诺产生小代价。
3. **倒计时**：给一个外部期限（"三个月内"）。

## 6. 收账三问（兑现时必答）

1. **是原承诺吗？** 兑现内容是否回应了当初承诺的那件事（不是别的事）。
2. **与 canon 冲突吗？** 兑现方式是否违反 `FACT-*`。
3. **来得及吗？** 是否在读者遗忘前发生（超窗口即 `OVERDUE`）。

## 7. 反面案例（只埋不收）

- 第 3 章给主角一件"关键时刻能救命"的物品，到第 60 章未再出现。
- 第 5 章说"他其实不是亲生的"，第 80 章仍未解释。

**判定**：超过预期窗口且无任何强化记录 → `OVERDUE`，必须处置。

## 8. 过期处置模板

```markdown
## OVERDUE：PROMISE-07
- 埋设：ch3# "这本笔记会救你一次"
- 距今：21 章
- 处置 A：提前收回（在下一章设计一次"笔记生效"）
- 处置 B：明确延后（让某角色提及"笔记还在"，重新激活记忆）
- 需作者确认：A / B
```

## 9. 与叙事状态对账

- 台账是"人可读"的账本；`narrative-state-store.json` 的 PromiseLedger 是"机器可读"的状态。
- 二者只允许单向差异：台账可更细，PromiseLedger 必须覆盖所有 `硬承诺`。
- **禁止**由本专家写入 `narrative-state-store.json`；提交由编排器在最终正文选定后完成。
